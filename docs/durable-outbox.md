# Durable native outbox

Named on-site authoritative hubs support a current-user private, typed journal for send, presence, acknowledgment and claim requests. The shared bearer token authenticates access to the hub; it does not establish per-agent roles. Legacy manual spool commands remain available. Named legacy candidates with a global provider and no configured global token retain their existing unauthenticated write path, with no durable replay guarantee. Explicit file/env providers or a configured global token never fall back when credential resolution fails; existing journals still fail visibly if credentials are removed. Cloud candidates do not grant claims through this path.

Writes append and sync a stable request ID before attempting transport. Ordered replay stops at an indeterminate request. `outbox status` shows retained IDs, `outbox flush` drains the existing queue without submitting a second operation. MCP calls also attempt a drain on reconnect. A retained or indeterminate result includes its request ID and explicitly warns against retrying as a new submission. Authentication and validation failures are permanent failures, not offline transport success. Capacity errors are visible; the journal is never silently pruned.

Concurrent native submissions and flushes wait for an existing journal writer
using their original twelve-second transport deadline. Lock acquisition uses
bounded exponential backoff with jitter, with each sleep capped to the remaining
budget. Acquisition is attempted once more after the final sleep, even if the
scheduler wakes after the deadline, because the writer may have released its
lock while the caller waited. If that attempt is still busy, no further sleep
is scheduled. Waiting, successful acquisition and a scope-rebind reopen do not
start another transport deadline; an exhausted budget permits no new outbound
attempt. Exhausted submission contention explicitly reports
that no new request was retained. A flush keeps the original retained request
IDs. Only lock contention is retried: custody, corruption and scope failures
keep their existing refusal semantics, and no enqueue or transport result is
retried as a new submission. The finite budget bounds retry scheduling; it is
not a real-time guarantee for filesystem calls or a suspended process.

Send and acknowledgment entries have no automatic age cutoff. Presence and claim requests retain their intrinsic deadlines. Never-attempted expired requests cannot introduce effects. Attempted presence requests can retrieve their original cached result after expiration to repair PostgreSQL history without resurrecting live presence. Claim replay atomically checks the actual returned lease expiry and exact current authoritative lease record, including original timestamp, status and scope. Release, same-agent replacement, contention and resolution cannot revive a cached grant. The check observes authority at that instant; it cannot promise a lease remains unchanged after the response. An ambiguous grant remains pending; replay does not grant it again or assert ownership offline.

The native hub retains permanent Redis replay memos for send, acknowledgment and presence. This avoids losing deduplication or delayed PostgreSQL repair identity. These memos contain replay results and payload fingerprints and consume storage; operators must budget capacity. There is no automatic memo maintenance subsystem in this change. Removing memos while journals can still replay, evicting them under memory pressure, losing Redis persistence, or restoring an older Redis snapshot can invalidate the at-most-once guarantee. The journal does not compensate for loss of the hub's accepted-request record.

Durability depends on Redis persistence and retention of both stream and memo keys. Disposable validation uses AOF with `appendfsync always` and performs an actual stop/start of the same Redis container and data volume. That proves the tested restart path only, not arbitrary power-loss zero-loss, a nonpersistent Redis deployment, or production restart acceptance. Production persistence and eviction configuration require separate operator evidence.

When PostgreSQL is configured, replay returns Applied only after a bounded synchronous idempotent history write. Redis acceptance followed by PostgreSQL failure returns Pending, retaining the original request ID for repair. Without PostgreSQL configuration, Applied denotes Redis acceptance only. Existing PostgreSQL presence history gains nullable replay identity columns and a partial unique index; legacy rows keep their existing semantics.

Windows storage requires protected current-user owner-only ACLs on the held file and parent handles. Unix storage requires owner-only directory/file modes and rejects aliases. Wine filesystem ACL projection does not qualify native Windows private storage. Journal scope is bound to a fingerprint of the full configured candidate list (`candidates_fingerprint`), so any candidate edit changes it. Retained work is never replayed to a different scope: a write or flush against a journal with retained requests fails visibly, and `outbox status` reports `scope_mismatch` with the bound and current scope prefixes and whether rotation is `automatic`, `explicit` or `blocked`. A journal with no retained requests is retired automatically on the next write or flush. `outbox rotate` can retire expired presence/claim requests only when they were never attempted. Attempted requests remain blocked even after expiry, because their original identity may still be required to recover acceptance or repair PostgreSQL history. Replay them with the previous configuration before changing scope. If a concurrent caller has already rebound the journal and queued current-scope work, flush reopens it once and drains that work; contention or further scope changes fail visibly.

Retirement preserves the original bytes and private permissions at `journal.retired-<origin>.jsonl` beside the active journal. Inspection retains its exclusive source-file lock through the move, so a cooperating old-scope writer or second rotation cannot enter an unlocked inspection-to-retirement interval. Opening validates the held source against the active path only after acquiring its lock; every production append validates that identity again. Thus a descriptor opened before another caller's retirement cannot append into the detached archive. The source-file lock and these identity checks serialize cooperating namespace moves without a lock-file format. The one addition is the empty `journal.lock`, which holds no data and exists only so a migration, which vacates the active path between two renames, can exclude writers from creating a journal there (see the recovery section below). An observed source replacement refuses retirement and preserves both files.

Windows journal handles permit deletion sharing and carry DELETE access so `SetFileInformationByHandle` can rename the exact locked handle with `ReplaceIfExists=false`. Linux uses `renameat2(RENAME_NOREPLACE)` while holding the source lock. Both primitives atomically refuse an existing archive; there is no exists-then-replacing-rename fallback. Unsupported Unix platforms and Linux filesystems without this primitive fail closed. Tests force intervening writes, source replacement, a second rotation and archive collisions using owned private fixtures. These locks coordinate callers using this implementation; Unix advisory locking cannot constrain raw filesystem mutations or older clients that lack the post-lock active-path check. Upgrade concurrent clients before rotating journals.

## Recovering after the authority or candidate list changed

Replaying under the previous configuration is only possible while that configuration still reaches an authority that answers to its identity. When the hub's `hub_identity` is renamed or moved (dtm-p1gen7, 2026-11-04: `asuspro13` became `dtm-work` with eleven requests retained), the previous identity is rejected and retained work cannot be drained the documented way. `agent-bus outbox migrate` is the supported recovery. It never replays anything; it moves the journal onto the current candidate list and says exactly what became of each request.

`outbox status` shows what the decision depends on. Each request reports `age_ms`, `attempted` and `stale` (older than `stale_after_ms`, seven days), and the summary counts `never_attempted`, `attempted_unsettled` and `stale`. Sends and acknowledgments still never expire by age, so a forgotten queue is made visible rather than dropped. When the journal is bound to another candidate list the report adds `recovery`, the command to run.

`migrate` classifies each retained request under one exclusive lock on the old journal.

- A request whose replay was never attempted cannot have had any effect on the previous authority (`attempted` is made durable before any transport call). It is carried to the current candidates with its original request ID, creation time and expiry, behind the same private-storage checks. An unsent presence or claim whose own deadline already passed is reported as expired and not carried.
- A request that was attempted and never settled may have been accepted by the previous authority, which the new one cannot recognise. It is never re-sent. The migration refuses while one exists, listing the IDs. `--include-attempted` archives it, listed as `abandoned`, once the operator accepts that its outcome is unknown. Replay it first under the previous configuration when that is still possible.
- `--archive-only` archives unsent requests too instead of carrying them: an explicit dead-letter.
- `--dry-run` prints the plan, `would_succeed` and the `blocked` IDs, and changes nothing.

The report lists `carried`, `expired`, `archived` and `abandoned` entries by request ID, operation, topic, thread (or agent, for presence) and age. It never contains a message body.

Order is what makes it crash-safe. The carried requests are written in full to `journal.migrating-<origin>.jsonl` first. Then the old journal is renamed to `journal.migrated-<origin>.jsonl` (the existing atomic no-replace rename, bytes untouched). That rename is the commit point. Then the staging journal is renamed into place with the same primitive.

A migration holds the directory lock `journal.lock` throughout, and every writer takes it, briefly, to finish an interrupted migration and to open or create the active journal. So no writer can create a fresh active journal in the gap between the two renames and strand the staged requests behind newer ones. The lock coordinates callers using this implementation; as with rotation, upgrade concurrent clients before migrating.

A stop between the two renames leaves the complete staging journal beside its `journal.migrated-` archive. The next write, flush or `migrate` finishes the move. Until then `status` describes the staged journal, so its requests are counted and the legacy-write guard still refuses to pass a write ahead of them, names it in `interrupted_migration`, and `migrate --dry-run` reports it without renaming anything. A staging journal whose `journal.migrated-` archive does not exist never reached the commit point. It may be a copy of a journal that is still live, or whose requests an earlier configuration has since delivered, so it is never promoted. It is left in place and listed as `stale_staging`; the next `migrate` of the same origin sets it aside as `journal.migrating-<origin>.partial.jsonl`, never deleting it.

A write or flush against a journal bound elsewhere with retained requests still fails visibly and now names `outbox migrate`. A journal with no retained requests is still retired automatically.
